## 1. 全体像

生徒ごとに進度が異なることを前提とし、**入門 → 実践 → 応用 → 発展**の4段階で構成する。
月別・回数別の固定進行にはせず、各段階の到達課題が確認できた時点で進級する。

| 段階 | 使うもの | ひとことで言うと | 教材テキスト | 講師の関わり方 |
|---|---|---|:--:|---|
| **入門** | Arduino＋ブレッドボード | 部品ひとつひとつの仕組みを知る | **あり**（9本） | 見本・手順・助言を多く使ってよい |
| **実践** | ロボットカー（キット） | 部品をロボットに載せて、課題を解く | **あり**（12本） | ヒントを出し、答えは教えない |
| **応用** | **自作ロボット** | 自分のロボットを設計して作る | **現段階では作らない** | 必要なときだけ相談に乗る |
| **発展** | **自作ロボットの改造** | 新しい対戦に向けて作り替える | **現段階では作らない** | 技術相談・設計レビュー・問題整理の支援役 |

**入門はロボットカーを使わない。** ブレッドボード上で部品を単体で動かし、仕組みを確かめる段階。
**実践はロボットの組み立てから始まり、Bluetoothでの対戦までを行う。** ここでキットを使い切る。

```
┌─ 教材テキストあり ───────────────────────────────┐
│                                                  │
│  入門（9本）              実践（12本）            │
│  ロボットカーを使わない  →  ロボットを組み立てる   │
│  ブレッドボードで         入門で知った部品を       │
│  部品の仕組みを知る        ロボットに載せる        │
│                           ＝Bluetooth対戦まで     │
│                           ＝キット完成            │
└──────────────────────────────────────────────────┘
                        ↓
┌─ 教材テキストは現段階では作らない ───────────────┐
│                                                  │
│  応用                     発展                    │
│  自分のロボットを      →  新しい対戦に向けて       │
│  設計して作る              改造する                │
│                                                  │
└──────────────────────────────────────────────────┘
```

### 応用・発展のテキストを現段階では作らない理由

**将来的に作らないという意味ではなく、着手の順序の問題。**
まず入門・実践の改訂を仕上げ、応用・発展は当面**指導員向けの到達課題と観察ポイント**（本書 §4・§5）で運用する。

実際に運用してみないと、生徒がどこでつまずくか・どんな支援が要るかが分からないため、**運用の記録がたまってから書く**ほうが実態に合ったものになる。

なお、この2段階のテキストを作るときも、**手順書の形にはしない**。
「何を作るか」「どう改造するか」を生徒が決める段階であり、手順書を用意すると方針書 §12 の「正しい作り方を教える資料」に戻ってしまう。作るとすれば、考えるための問いかけ・チェックリスト・参考事例集といった形になる。

### 入門をすべて終えてから実践に進むわけではない

方針書 §2 のとおり、進級は「教材を全部終えたら」ではなく「**必要な経験と能力が確認できたら**」行う。
入門の到達課題をクリアすれば実践に進んでよく、入門の残りのレッスン（超音波・サーボなど）は、実践でその部品が必要になった時点で戻って行う。

### 部品と段階の対応

「入門で部品を知る → 実践でロボットに載せる」という受け渡し。

|部品|入門（部品を知る）|実践（ロボットに載せる）|
|---|---|---|
|赤外線受信|05|14・20|
|ブザー|06|20|
|障害物センサー|07|15|
|超音波センサー|08|17|
|サーボモーター|09|17|
|トラッキングセンサー|**入門に置かない**|16|
|Bluetooth|**入門に置かない**|19|
|WiFi|**入門に置かない**|18|

トラッキングセンサーと通信モジュール（Bluetooth・WiFi）は、**入門に単体レッスンを置かず、実践で直接ロボットに載せて扱う**。
旧L13（トラッキングセンサー単体）・旧L19（BluetoothでLED）は削除済みで、復活させない。

### 現行教材の状況

現行21レッスン（20ファイル・L04-05が2回分）。13・19は欠番。
修正の必要性：**大**＝構造から作り直す ／ **中**＝節の追加・分割 ／ **小**＝加筆で足りる

- 変数と型（`int` `float`）、四則演算、`delay()`

### 到達課題

**10cmでブザーが鳴る人感センサーを作る**（入門07の「やってみよう」）
— ブレッドボードにセンサーとブザーの回路を組み、定規で測りながら感度を調整して、狙った距離で鳴るようにする。

回路を作る（工作）・センサーを読む（プログラミング）・調整して狙いどおりにする（試行錯誤）という入門の要素が1つに入っており、定規で測れば成否がはっきりするため。

## 7. 全レッスンに共通する修正

実地で全20ファイルを点検した結果、次の2点はほぼ全レッスンに共通する。

### ① 「まとめ」が知識の要約になっている

現行の「まとめ」節は**教えた知識の要約**になっており（例：L06は `go_Advance()` の説明、L22は `switch` 文の書式）、生徒が自分の活動を言語化する構造になっていない。最も近いのは L15 の「出来たことをチェックしよう」だが、これも技能の自己チェックにとどまる。

**修正**：全レッスン末尾の「まとめ」を次の形式にする。

```markdown
## まとめ

### できるようになったことをチェックしよう

- [ ] （「このレッスンで身につける力」と同じ項目）

### まとめページに書こう

Googleサイトの自分の**まとめページ**に、次の4つを書こう。

1. **やったこと**
2. **わかったこと**
3. **感じたこと**
4. **つぎやること**

**スクリーンショットか画像を必ず1枚入れること。**

> まとめは1日に1回書く。
> 複数のレッスンを進めた日も、1つのレッスンが1回で終わらなかった日も、まとめは1回。
```

### 「まとめ」の運用

|項目|内容|
|---|---|
|書く場所|Googleサイトの生徒ごとの**まとめページ**|
|書く頻度|**1日1回**。複数レッスンを進めた日も、1レッスンが1回で終わらなかった日も1回|
|必ず書くもの|やったこと／わかったこと／感じたこと／つぎやること の**4つすべて**|
|必ず入れるもの|**スクリーンショットか画像を1枚以上**|

頻度がレッスン単位ではなく1日単位のため、**そのレッスンで何ができるようになったかのチェックリストは各レッスンのテキスト側に置く**。
まとめページには、チェックリストを見ながら上記4項目を書く。

> 経験項目 #8 スクリーンショットを撮る ／ #18 データをクラウドにアップロードする ／ #20 活動記録をデジタルデータとして残す ／ #75 制作過程を写真や文章で残す ／ #76 自分の活動を振り返る に対応する。

### ② 「やってみよう」の工程が任意扱いになっている

「（工夫できる課題）」という但し書きで終わっているレッスンが複数あり、改良が必須工程になっていない。方針書 §5 は「一度作って終わりにせず、最低1回は変更・改善を考えさせる」としている。

**修正**：各レッスンに**必ず1つ**、具体的な「やってみよう」の課題を置く。「工夫してみよう」ではなく「◯◯になるように変えてみよう」と目標を示す。

### ③ 不足している文法解説

|不足している内容|現状|対応案|
|---|---|---|
|`for` 文・`while` 文|旧L04-05・L17・L21のサンプルコード内に**解説なしで登場**する|入門04（LED点滅）の「やってみよう」として扱う|
|`switch` 文|入門09（サーボ）のサンプルに無解説で登場し、解説が出るのは実践21（最後）|入門09に解説を追加する|
|自作関数 `void 関数名(){}`|組み立て以降ずっと使っているが、解説は最終レッスンのみ|実践11（`motor_driver.h` 導入時）で「関数とは何か」を扱う|

> **固定のレッスンとして差し込まず**、既存レッスンの中で扱う。方針書 §11「固定進行にしない」に従う。

## 8. 技術統一事項

既存サンプルコードを実地で調査して判明した不整合と、その統一方針。
段階構成とは独立して、コードレベルで先に片付けられる項目。

### ① モーター制御の変数名が3系統に分裂している

同じ動作をするコードが3通りの書き方で存在し、生徒が前回のコードを流用できない。

|系統|使用レッスン|変数名|
|---|---|---|
|A|L04-05, L06, L10, L12, L17|`speedPinR` / `RightMotorDirPin1・2` / `speedPinL` / `LeftMotorDirPin1・2`|
|B|L14|`m1`〜`m4` / `e1`, `e2`|
|C|L20, L21|`speedPinRight` / `dir1PinRight・2` / `speedPinLeft` / `dir1PinLeft・2`|

**統一方針**：`motor_driver.h` を新設して1系統に集約し、全ロボットレッスンで `#include` する。
実践L05（組み立て(2)）で導入し、以降すべてのロボットレッスンで同じものを使い続ける。
応用段階（オリジナルロボット作成）では、生徒が自分の機体に合わせてこのファイルを調整する（＝既存コードを読んで変更する経験＝経験項目#32・#60）。

### ② 右モーターPWMピンが L17 だけ異なる

|レッスン|右モーターPWM|
|---|:--:|
|L04-05, L06, L10, L12, L14, L20, L21|**D9**|
|L17|**D3**|

L17でサーボモーターがD9を使うため、途中でピンが変わっている。

**統一方針**：**最初からD3に固定**し、D9をサーボ用に空けておく。
後で変えると「前回動いたコードが動かない」状態になるため、最初から空けておく。

### ③ L14のコメントで左右が逆になっている

```c
// Lesson_14/sample/Lesson_14_sample.ino
#define m1 7   //右モーターMA1   ← 他の全レッスンでは 7・8 は「左」モーター
#define m2 8   //右モーターMA2
#define m3 12  //左モーターMB1   ← 他の全レッスンでは 12・11 は「右」モーター
#define m4 11  //左モーターMB2
```

他の全レッスン（系統A・C）では **12・11 = 右モーター / 7・8 = 左モーター**。

**対応**：実機で配線を確認したうえで修正する。コードの動作自体は左右対称なら問題なく動いてしまうため、**実機確認が必須**。

### ④ ブザーの扱いが一貫していない

`BUZZ_PIN`（D13）が定義されているのは L04-05・L17・L21 のみ。

**統一方針**：全ロボットレッスンでブザーを**搭載したまま**にし、動作確認の手段として使う。
「今どの処理に入っているか」を音で知る＝デバッグの手段として定着させる（経験項目#34）。

### ⑤ サンプルコードの重複（L21）

```
Lesson_21/sample/lesson_21_sampleA/lesson_21_sampleA.ino
Lesson_21/sample/lesson_21_sampleB/lesson_21_sampleB.ino
Lesson_21/sample/v2smartcar-lesson8A/v2smartcar-lesson8A.ino
Lesson_21/sample/v2smartcar-lesson8B/v2smartcar-lesson8B.ino
```

`v2smartcar-lesson8A/B` は osoyoo のオリジナル、`lesson_21_sampleA/B` が改造版と思われる。
最新コミット（`c4e7e4f`）でコメントアウトによるA/B切り替えに対応済み。

**対応**：どれを正とするか決め、使わないものは `archive/` へ移すか削除する。教材本文からの参照も合わせて修正する。

### 作業順序

`motor_driver.h` は全ロボットレッスンのコードに影響するため、**個別レッスンの改訂より先に確定させる**。

1. `motor_driver.h` の関数名・ピン定義を決める
2. 実機でピン配置（特に③の左右）を確認
3. 全ロボットレッスンのサンプルコードを差し替え
4. 各レッスン本文のコード掲載箇所を修正
