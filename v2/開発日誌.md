## 2026-09-25（2）

### 議題：入門編の修正（ライブラリ更新・ブレッドボード・提出フロー）

#### 1. IRremote を最新版（v4）に更新

入門05・06・09 が IRremote 2.x のAPI（`IRrecv` / `decode_results` / `irrecv.decode(&results)`）で書かれていた。

**Arduino IDE に入るライブラリは1バージョンだけ**なので、入門だけを新APIにすると、
旧APIのままの実践14・20・21 がコンパイルできなくなる。
そのため **IRを使う6レッスン（05・06・09・14・20・21）をまとめてv4に移行**した。

**IRコードの持ち方を変えた。** v2 の `results.value`（`0xFF18E7` のような8けた）から、
v4 の **`IrReceiver.decodedIRData.command`（`0x18` の2けた）**にそろえた。

|ボタン|旧|新|
|---|---|---|
|▲|0xFF18E7|**0x18**|
|▼|0xFF4AB5|**0x4A**|
|◀|0xFF10EF|**0x10**|
|▶|0xFF5AA5|**0x5A**|
|OK|0xFF38C7|**0x38**|
|#|0xFFB04F|**0xB0**|

旧の値は NEC の32ビット生データ（`address` `~address` `command` `~command`）で、
3バイト目が `command`。つまり `0x00FF18E7` → `0x18` という機械的な対応になる。
入門05の記録表・クイズ、06・09・14 の `#define`、20・21 の弾コードをすべてこの形に統一した。

対戦ゲームの弾は Sony 12ビットの `0xAAA` / `0xBBB` だったが、
教材全体をNECにそろえるため **NECの command `0xAA` / `0xBB`** に変更した。

**付随して変わったこと**

- ライブラリの入れ方を、osoyoo の zip ダウンロードから**ライブラリマネージャ**に変更（入門05）
- 06・14・20・21 は `DISABLE_LED_FEEDBACK` を指定。v4 の受信確認LEDは `LED_BUILTIN`（D13）で、**ブザーと同じピン**のため
- 06 は `lastCommand` 変数を追加。旧コードは `decode()` の外で `results.value` を参照していた
- 20・21 の `buttonState` を廃止。送信後に受信を再開させるためのフラグだったが、v4 の `IrReceiver.restartAfterSend()` で足りる
- 20・21 の送信ピンは `#define SEND_PIN 3` で明示。v4 は送信ピンを選べる（v2は固定だった）
- 14・20・21 に `#define DECODE_NEC` を追加してフラッシュを節約

**ENA = D9 の判断は変わらない。** v4 でも受信は Timer2 を使うため、D3 の `analogWrite` とは両立しない。

#### 2. ブレッドボードの指示を追加（06・07・08）

配線図はあるが「ブレッドボードで組む」という指示がなく、
何をどこにさすのかが本文から読み取れなかった。3レッスンに手順を追加した。

- Arduinoの 5V / GND をブレッドボードの ＋列 / −列に引く
- 各モジュールのVCC・GNDはその列から分ける
- 信号線だけをArduinoのピンへ直接つなぐ
- 「なぜこうするのか」（横一列がつながっている）の説明を添えた

チェック項目に **「ブレッドボードのどのあなとどのあながつながっているか説明できる」** を入れ、
理解しているかを口頭で確認できるようにした。

#### 3. 超音波センサーの配線に注意書きを追加（08）

配線図がセンサーを**正面から**描いているのに対し、**たんしはうら側**にある。
図のまま左から順にさすと左右が逆になる。
「数えて合わせるのではなく、書かれている文字（VCC/Trig/Echo/GND）を1本ずつ読んで合わせる」
という指示と、たんし対応表、VCC/GND逆ざしの警告を追加した。
「確認」のトラブル表にも同じ注意を追記。

#### 4. ファイルの提出フローを入門全レッスンに追加

保存の指示はあったが、**提出（クラウドに上げる）の指示が無かった**。
入門01〜09の「まとめ」に **「ファイルを保存してクラウドに上げよう」** の節を統一して追加した。

- そのレッスンで作るファイル名を具体的に明示（例：`0410makoto08_1` 〜 `08_3`）
- **スケッチはフォルダごと**「生徒共有」の中の自分のフォルダに入れる
- `.ino` だけを運ぶと開けなくなる理由を説明
- チェックボックス2つ（名前の形／提出できたか）

あわせて**連番の区切りを `_1` `_2` に統一**した。05・06 だけ `-01` `-02` で、
他の5レッスンと形がちがっていたため。レッスン02の命名ルールにも連番の書き方を明記した。

#### 検証

`avr-g++` で全30本の文法チェックを再実行し、すべて通過。
IRremote v4・WiFiEsp はスタブヘッダで代替している。
本文のコードブロックとサンプルの `.ino` が一致していることも確認した。

**実機検証は未実施。** 特に次の点は実機で確かめること（指示どおり「後で要チェック」）。

- ライブラリマネージャで入る IRremote の最新版で、実際に `command` が表の値になるか
- 20・21 の弾（NEC `0xAA` / `0xBB`）が正しく撃てて、当たったら倒れるか
- 送信直後に `restartAfterSend()` で受信が戻るか（自分の弾を自分で拾わないか）
- 06・14・20・21 で `DISABLE_LED_FEEDBACK` によりブザーが誤作動しないか

#### 残っていること

- 入門05の画像（library2〜4.png、serialmoniter2.png）は**旧バージョンの手順・表示のまま**。撮り直しが必要
- 実践18の WiFiEsp も osoyoo の zip 配布で古い。今回の指示の範囲外なので未対応
- 入門のサンプルフォルダ名が旧番号のまま（`lesson_08_arduino_sample` など）

#### 判明したこと：ENA = D3 は赤外線レッスンでは成立しない

書き換えの途中で、設計書 §8② の「最初からD3に固定」が物理的に成り立たないことが分かった。

IRremoteライブラリは Arduino UNO で **Timer2** を使う。
受信時は `enableIRIn()` が50µsサンプリング割り込みのために Timer2 をCTCモードへ再設定し、
送信時は `enableIROut()` が38kHzの搬送波を Timer2 で作る。
UNOで **Timer2 が担当するPWMピンは D3 と D11** なので、
赤外線を有効にすると **`analogWrite(3, …)` が正しく動かなくなる**。
（D11 は `digitalWrite` しか使わないので影響しない）

D5 は WiFi/Bluetooth の SoftwareSerial が占有しているため、
**全レッスン共通の1ピンにする解は UNO のタイマー構成上存在しない。**
旧教材が 14・20・21 で ENA を D9 にしていたのは、この制約の回避だったと思われる。

**決定**：`motor_driver.h` に `USE_IR_ROBOT` スイッチを設け、赤外線を使う 14・20・21 だけ ENA を D9 にする。
該当レッスンの本文に、つなぎかえる理由と「終わったらD3に戻す」注記を入れた。

|レッスン|ENA|理由|
|---|:--:|---|
|11・12・13・15・16・18・19|D3|—|
|17|D3が必須|サーボ（Timer1）が D9・D10 の PWM を潰すため|
|**14・20・21**|**D9**|IRremote（Timer2）が D3 の PWM を潰すため|

## 2026-09-23

### 議題：現行21レッスンを4段階構造へ再編し、v2として全レッスンを執筆

#### 経緯

『ロボ部カリキュラム 編集方針』（Claudeへの作業指示書）に基づき、既存教材の再構成に着手した。

当初は「現行レッスンを土台に、固定順序の30レッスン構成へ再編する」案を作成したが、方針書 §11「編集時に避けること」に

- 月別・学期別の固定進行にする
- 「○回受講したら進級」とする
- 全員が同じ速度で進む前提にする

とあり、この案は前提から外れていたため破棄した。方針書 §2 が求める**入門／実践／応用／発展の4段階構造**へ作り直した。

あわせて `アイアルク_経験項目_新カリキュラム設計.xlsx` を確認。96の経験項目が6カテゴリに整理され、「ロボ部 入門／実践／応用／発展」の列が空欄になっていることから、これが設計の入力欄だと判断し、各段階の記述を経験項目番号に対応づけた。

#### 決定事項

**段階の定義**

| 段階 | 使うもの | 教材テキスト |
|---|---|---|
| **入門** | Arduino＋ブレッドボード（ロボットカーを使わない） | あり・9本 |
| **実践** | ロボットカー（組み立て〜Bluetooth対戦＝キット完成） | あり・12本 |
| **応用** | 自作ロボット（オリジナルロボット作成） | 現段階では作らない |
| **発展** | 自作ロボットの改造（新しいロボット対戦） | 現段階では作らない |

分類基準は**ロボットカーを使うかどうか**。入門は部品を単体で知り、実践でロボットに載せる。

応用・発展のテキストを作らないのは着手順序の問題であり、将来的に作らないという意味ではない。運用の記録がたまってから書くほうが実態に合う。作る場合も手順書の形にはせず、考えるための問いかけ・チェックリストの形にする（方針書 §12）。

**レッスン番号**

#### レッスンテキストの構成

方針書 §5 に沿って全21本を統一した。

```
ミッション → 身につける力 → 今回使う技術 → ミッションの準備
→ メインミッション → 確認 → やってみよう → まとめ
```

セクション名は「制作・挑戦→メインミッション」「テスト→確認」「改良→やってみよう」「振り返り→まとめ」とした。

**まとめの運用**

- 書く場所：Googleサイトの生徒ごとのまとめページ
- 頻度：**1日1回**（複数レッスンを進めた日も、1レッスンが終わらなかった日も1回）
- 必ず書く4項目：やったこと／わかったこと／感じたこと／つぎやること
- **スクリーンショットか画像を必ず1枚**

頻度がレッスン単位でなく1日単位のため、**そのレッスンのチェックリストは各レッスンのテキスト側に置き**、生徒はそれを見ながらまとめページを書く。「全部でなくてよい」という逃げ道は置かない。

#### 「確認」を実質的な工程にした

現行教材では動作確認が曖昧だったため、次を各レッスンに置いた。

- **電源を入れる前の配線チェック**（04・11）— まちがった配線で電源を入れると部品がこわれるため
- **通信できたかの確認**（18・19）— つながっていないのに走らせても動かない
- **センサー値の確認**（15・16）— 走らせる前にシリアルモニターで値を見る
- **症状別トラブルシュート表**（全レッスン）

#### ブザーをデバッグの道具として一貫させた

入門06で鳴らし方のパターンを作り、以降は「いまどの処理に入っているか」を音で知らせる用途に統一した。`motor_driver.h` に `beep(回数, 長さ)` を用意。

レッスン11で「音は鳴るのに走らないなら、原因はプログラムの外（配線や電池）」という切り分けを教え、13では区間ごと、15では判断ごと、17では判断内容を音で知らせる設計にした。

#### 入門と実践の接続

段階を分けたことで、入門で得たものを実践で使う導線が必要になった。

| 入門で作るもの | 実践で使う場所 |
|---|---|
| 05 IRコード記録表 | 14（リモコン操縦）、20（対戦） |
| 11 速さと距離の表 | 12（チキンラン） |
| 13 90度曲がる時間 | 14、21 |
| 09 サーボの首ふり | 17（周囲スキャン） |
| 09 `switch` 文 | 14、21 |

トラッキングセンサー・Bluetooth・WiFiは**入門に単体レッスンを置かない**（旧L13・旧L19は復活させない）。実践で直接ロボットに載せて扱う。

#### 応用・発展で「正解」を渡さない設計

レッスン17と21は、応用段階への橋渡しとして設計を変えた。

- **17**：サンプルコードを「正解」ではなく「たたき台」と明記。迷路の解き方（一番広いほうへ／右手法／止まらず走る）を提示し、**選ばせて理由を説明させる**
- **21**：必殺技を「①困っている場面 → ②解決方法 → ③動きの順番 → ④かかる時間」の順に設計させ、**使って直してまた使う**ところまでを到達課題にした
